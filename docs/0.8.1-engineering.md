# Xenon360 0.8.1 engineering notes

## Scope and public references

The 0.8.0 development checkpoint was preserved before the processor changes. Public qualification uses synthetic fixtures and independently documented processor semantics. Private validation inputs are neither identified nor distributed here; no claim about any particular game, program revision, linked library, or SDK build is implied.

Public implementation references include Xenia's [opcode table](https://github.com/xenia-project/xenia/blob/121bf93cbe2c23fe0a47f1f43e3f050df46e976d/src/xenia/cpu/ppc/ppc_opcode_table_gen.cc) and [VMX emitter](https://github.com/xenia-project/xenia/blob/121bf93cbe2c23fe0a47f1f43e3f050df46e976d/src/xenia/cpu/ppc/ppc_emit_altivec.cc), pinned to one revision. These provide independent implementation context, not physical-console execution evidence.

## Processor corrections

`lvrx128` has mask/value `fc0007f3/10000443`. Its destination bank bits overlap encodings used by later PowerISA `vabsduh` and `vcmpneh.`, neither of which belongs to the Xenon instruction set. Language preparation excludes the conflicting constructors and adds the VMX128 load-right constructor. The associated regression uses generated instruction words, not a published proprietary binary excerpt.

The load zeroes its destination when the effective address is aligned. Otherwise it reads the aligned 16-byte block and places its first `EA & 15` bytes at the right end of the vector, zeroing the remaining bytes. RA=0 contributes zero. An aligned load does not read memory.

`vpermwi128` selects each destination word from a source word using the corresponding two immediate bits, with the most significant selector selecting the most significant word. `vrlimi128` rotates source words left and inserts only lanes selected by mask bits 3 through 0, preserving the other destination lanes. Bit 4 of the encoded mask does not select a lane. Both operations snapshot inputs before assigning the destination, including aliases. They now emit native integer p-code rather than opaque userops. Existing userop declarations are retained to avoid incidental index churn.

The processor language has minor revision 1.1. Validate upgrades only on a copy of an existing project; fresh synthetic imports are part of qualification. No analyzer logic or calling convention was changed.

## Limits and withheld changes

Desktop Direct3D headers cannot establish console-side COM layouts or enum meanings. No proprietary function mappings, reference bytes, graphics identification, or SDK-dependent automatic naming are included. Ambiguous library boundaries and aliases remain unsupported.

Existing Havok recognition, confidence levels, and opt-in callback naming are unchanged. Floating-point VMX operations that still emit opaque userops remain unresolved. Native p-code tests establish the specified lane and memory behavior, not execution on physical Xbox hardware.

## Reproduction and rollback

Build with the supported Ghidra and JDK pair using the README commands. `smokeTest` executes processor tests without emulated userop callbacks and retains synthetic results under `build/smoke`. No private research input is needed for these public checks.

Keep the previous extension package and original project backups when testing an upgrade. Roll back by restoring the earlier package in a separate settings profile and reopening a retained project copy. Do not downgrade a project already saved with a newer language revision in place.
