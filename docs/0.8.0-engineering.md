# Xenon360 0.8.0 engineering notes

This candidate targets Ghidra 12.2 and Java 25. The module name and language ID remain `XenonVMX128` and `PowerPC:BE:64:Xenon-VMX128-32addr`. The Gradle 9.1.0 wrapper is pinned by SHA-256. `buildExtension smokeTest` builds a complete installable ZIP and exercises it in isolated settings.

## Integrated behavior

The XEX loader still performs the verified save-helper bootstrap before general analysis. The compiler-helper analyzer makes the operation re-runnable, refuses conflicting ownership or defined data, and records residual CALL_RETURN overrides. Changing such overrides is opt-in because Ghidra does not preserve their authorship.

The Havok analyzer is automatic for the Xenon language. It validates descriptor relationships before labeling metadata. Missing, uniquely identified callbacks may receive function boundaries only after bounded control-flow preflight. Existing functions, data, labels and types take precedence. Callback naming remains opt-in and requires a source hash. Any failed disassembly after preflight aborts the enclosing analysis transaction.

An unconditional branch to an established function entry terminates a recovered callback as a tail call. This makes recovery independent of the later Shared Return Calls analyzer's flow classification. Unresolved branches and branches into an existing function's interior remain withheld; no target ownership or flow override is changed.

The automatic bounded-switch analyzer recognizes two exact MSVC byte-index forms: a contiguous unsigned `cmplwi`/`bgt` guard, fixed `lbzx` register flow, optional scale by four, and a relative `bctr` whose base is the following instruction. Tables must be initialized, read-only and non-executable. At most 256 entries, 512 matched tables and 4096 new code bytes per table are accepted. All case CFGs are checked before mutation; only default-named owners may be extended, with no clearing or ownership reassignment. Cancellation rolls back references, disassembly and body changes. Native tests cover valid scaled/unscaled tables, idempotency, cancellation and malformed/protected cases.

Evidence export and reference comparison are ordinary CodeBrowser plugin actions with file choosers, progress and cancellation. They share the analyzer's recognition code. Normal summaries use informational logging; errors use the analysis log. JSON is canonicalized and written through a temporary file followed by an atomic replacement where supported.

## Havok recognition boundaries

The supported metadata profiles are independent of version claims:

| Profile | Required evidence | Automatic scope |
| --- | --- | --- |
| Four-pointer Xenon hkTypeInfo | Class string, two executable callbacks, mapped vtable, exact constructor vptr store | Metadata labels/types and bounded unowned callbacks |
| Scoped six-field hkTypeInfo | Related plain/scoped names, executable callbacks, plausible target size, optional executable vtable | Metadata labels/types and bounded unowned callbacks |
| x64 four-pointer static initializer | Four mapped destination slots, constructor/getter/finish/cleanup relationships | Evidence export only |
| 32-bit hkClass/hkClassMember | Bounded unique members, offsets, mapped relationships and acyclic parent graph | Evidence export; no inferred instance type application |

The differently ordered Havok 7.1 six-field profile is deliberately unsupported. Archive versions and target strings do not prove the exact linked middleware build. No SDK payload, proprietary header or game binary is needed at runtime or included in the distribution.

Reference comparison is conservative: structural metadata and Ghidra's native similarity features may nominate review-only candidates. Short generic callbacks are not treated as unique identities. No function prototype, instance layout or ABI is transferred.

If a scan reaches its name or record limit, callback evidence remains provisional and automatic recovery/naming is withheld because class-specific uniqueness is unproven. Comparison rejects the same source hash regardless of hexadecimal letter case.

## Semantics and tests

Native p-code now models `vandc128`, left vector loads, and partial vector stores, including standard instruction counterparts. Tests cover all 16 offsets, all four VMX128 register banks, source/destination aliases, RA=0, preserved memory lanes and the aligned right-store no-op. They execute the actual emitted p-code without custom userop emulation. Six existing v0.7 golden mnemonics are retained.

Floating point fusion, estimates, saturation and compare-record behavior remain explicitly opaque where represented by userops. Passing mnemonic or p-code tests does not establish hardware equivalence for those instructions.

Supplemental developer validation can use separately supplied inputs and isolated projects; no proprietary datasets or private research case histories are included. Public smoke tests use synthetic fixtures. Timeouts count as failures even if a headless process exits zero. Developer scripts are not part of ordinary installation or analysis.
